pydle for teachers

pydle needs no accounts, no installation and no licence, so a class can be writing Python in the first minute of a lesson. GitHub is optional. It gives a student their own copy of the work and a history of it, and it is the only part that needs setting up in advance.

Open the Python editor Print the student setup sheet (PDF)

pydle is an editor. It has no roster, no assignments, no marking and no teacher dashboard. Students open it, write Python and keep their own files.

What a lesson looks like

Students open pydle.uk, make a project with a name, and press Run. Python is downloaded once by the browser, then the editor, console and turtle all work without a server. Work saves to that browser as it is typed, so a dropped connection or a closed tab costs nothing.

Programs can be downloaded as .py files at any point. That is the export path when you need to collect something, whether or not students have GitHub.

From year 9, GitHub should be the default. Work survives the device and keeps its history. GitHub accounts are for people aged 13 and over. Do not create accounts for students or let them share one. One account per person is GitHub's rule, and a shared login leaves two students with a repository neither of them can safely commit to.

Why not to do the GitHub setup in a lesson

Thirty sign-ups from one school address look like abuse. GitHub rate-limits account creation by source address, and a class behind a school filter shares one. In August 2026, a class of twelve hit Too Many Requests trying to sign up from their school filter, and the advice in GitHub Classroom's own discussion forum was to have students create accounts at home or to stagger them. One documented school case went further. The accounts were created, then suspended days later, and restoring them took four appeals over three weeks. This is current behaviour. Sign-ups from an unfamiliar or heavily shared address can also trigger extra verification on the spot.

  • Filtering. github.com is blocked or partly blocked on many school networks. Sign-in also needs api.github.com, and the editor needs cdn.jsdelivr.net for the Python runtime. You will discover the gaps on a class set of devices, not on yours.
  • Email verification. GitHub will not activate an account until the email is confirmed. School mail filters frequently quarantine those messages, and some domains refuse external sign-ups altogether. A student who cannot receive the mail cannot finish, and there is nothing you can do from the front of the room.
  • It takes two steps. pydle signs in with GitHub's device flow. The student reads an eight-character code off the screen and types it into github.com/login/device, then approves pydle. The code lasts fifteen minutes. Circulating to help thirty students type it is most of a lesson.

Before the lesson

The GitHub setup is preparation, a week ahead, not a lesson activity.

  1. Check the network on a student device, not a staff laptop. It needs pydle.uk, cdn.jsdelivr.net for Python and libraries, auth.pydle.uk and github.com, plus api.github.com if you are using GitHub.
  2. Check the browser. A current Chrome, Edge, Firefox or Safari. pydle needs WebAssembly.
  3. Check the year group is 13+ before you print anything that mentions GitHub.
  4. Print the sheet, one per student, or send the PDF through your usual channel. Hand it out a week before you need it.
  5. Run a clinic at lunch or after school for the students who did not manage it. One adult, a few devices.
  6. Take five minutes in the first lesson for the students who are connected. Make a project, run it, press Commit, and show the repository in a browser tab.

Students without GitHub work exactly as everyone else does.

What students get from GitHub

When a student signs in, pydle offers to create one private repository called pydle-workspace in their own account. Each project the student commits becomes a folder in it, with its files and its requirements.txt.

  • Work is saved to the device first and only reaches GitHub when the student commits, with a short message and a diff of what changed.
  • Every commit is kept, and any earlier version can be viewed or loaded back into the editor.
  • The repository belongs to the student. They can open it, download it, share it or delete it without asking, and it survives pydle.
  • Nothing else in their account is touched, and pydle never sees their password, their email or their other repositories.

GitHub grants the app read and write access to repositories in general. pydle's code only touches the repository it created, and GitHub's permission model does not enforce that. Worth knowing if your DPO asks.

Collecting and seeing work

pydle has no teacher view, so collection is manual whichever route you use.

  • Without GitHub, students use the download button in the toolbar and submit the .py file through your usual channel, or show you the screen at the end of the lesson.
  • With GitHub, per student, the repository is private, so a student has to add you as a collaborator on it, or make it public, before you can read it. For a class of thirty that is a lot of accepting.
  • With GitHub Classroom, if your school already uses it, an organisation and a classroom sit on top of the same repositories and give you the class view pydle does not have. It is extra setup, and it is the part pydle deliberately does not do.
  • Either way, the downloaded .py is the portable copy. Ask for that at the end of a unit even if the work is in a repository.

Shared, school and loan devices

  • The saved work belongs to the browser profile, not to the student. Two students on one profile see each other's projects.
  • Use a separate OS account or a guest profile per student where you can. In a private or incognito window the work is gone when the window closes, which is safe but useless for next lesson.
  • Forget this device, inside the GitHub panel, removes the GitHub sign-in from that browser. It does not delete the projects, so a shared machine still holds them.
  • To leave nothing behind on a shared machine, delete the projects in pydle, press Forget this device, then clear site data for pydle.uk in the browser settings.

What pydle stores, and where

Useful when the question reaches a data protection officer.

  • No pydle accounts, no mailing list, no analytics and no advertising scripts.
  • Code lives in the browser's own storage on the device, in the Origin Private File System with an IndexedDB fallback. It is not uploaded anywhere unless the student commits.
  • A GitHub sign-in token, if there is one, is stored in that browser's IndexedDB and nowhere else. Forget this device removes it.
  • Commits go to the student's own GitHub account, which is a separate service with its own terms and privacy policy. A private repository is visible to the student and anyone they invite.
  • The only server pydle runs is a stateless relay at auth.pydle.uk that passes GitHub's OAuth requests through. It stores nothing.
  • Nothing in pydle needs a real name. Ask students not to put personal details in project files or commit messages.

When it goes wrong

A student cannot reach github.com

Almost always filtering. Check api.github.com as well as the main site. The sign-in will fail even when the page loads. The student can carry on without GitHub.

"That code expired before it was approved."

The code lasts fifteen minutes. If they were slow, or were already signed in to GitHub on another account, the approval did not land. Start the sign-in again for a fresh code.

No verification email arrives

Check junk and quarantine first, then the school mail filter. Some domains block GitHub's mail outright. If it cannot be delivered, that student cannot use GitHub, and the lesson should not wait for it.

"The repository could not be created."

Usually the account already contains a repository called pydle-workspace, or the account is managed in a way that forbids creating repositories. Have the student sign in at github.com and look. Nothing on the device is lost either way.

A student is signed in as someone else

Press Forget this device in the GitHub panel, then sign in again. On a shared machine, do that before the next student starts, not after.

Work has disappeared

Saved work is tied to one browser profile on one device. Clearing browsing data, using a private window, or moving to another machine all lose it. If the student had committed, signing in again pulls the work back from GitHub.

The editor sits on "Loading..."

The Python runtime downloads from cdn.jsdelivr.net on first use. If that domain is blocked, nothing runs. Allowlist it and reload.

Two students are editing on one laptop

Use two browser profiles, or finish and download the work before the second student starts. Projects are shared across the whole profile.

Questions and problems
